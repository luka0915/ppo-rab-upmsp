# PPO-RAB: DRL-Driven Rollout and Adaptive Batching for Unrelated Parallel Machine Scheduling

Reference implementation of **PPO-RAB**, a deep reinforcement learning (DRL)
method for the **Unrelated Parallel Machine Scheduling Problem with
Sequence-Dependent Family Setups (UPMSP-SDFS)**, minimizing **Mean Weighted
Tardiness (MWT)**.

The agent is a PPO actor–critic that learns a **size-independent** policy: it is
trained on a single small instance and applied, without retraining, to larger
instances with different numbers of machines, job families, and jobs. At
scheduling time it combines a **DRL-driven rollout** with **critic-based
adaptive batching** to build a complete schedule under a wall-clock time limit.

This repository accompanies the paper *"Scheduling Unrelated Parallel Machines
with Sequence-Dependent Family Setups via DRL-Driven Rollout and Adaptive
Batching."* Inline comments map each component back to the paper's equations and
algorithms (e.g. Eq. 11–14 for the state, Eq. 16–20 for action features,
Algorithm 1–4 for batching/rollout/training/scheduling).

## Method overview

| Concept | Description |
|---|---|
| **State** `s = [s1,s2,s3,s4]` | max completion time, # idle machines, assigned weighted tardiness, # remaining jobs (Eq. 11–14, all 0–1 normalized) |
| **Action** | a (machine, job-family) pair; scored by a learned weight vector `ω` over 5 action features `[a1..a5]` (Eq. 16–20) |
| **Policy** | `q_a = ω · φ_a`, `p_a = softmax(q_a / τ)` (Eq. 21–22) |
| **Reward** | `Σ(-w_j T_j)` per step, minus the terminal MWT (Eq. 23) |
| **Adaptive batching** (Alg. 1) | the critic `V_ψ` decides how many consecutive same-family jobs to commit at once, expanding until the estimated value drops by more than tolerance `η` |
| **Rollout** (Alg. 3) | each above-average candidate action is rolled out to a complete schedule under the current policy; the best is committed (Alg. 4) |
| **Training** (Alg. 2) | PPO with GAE (Eq. 25), clipped surrogate (Eq. 26), and value loss (Eq. 27) |

Actor and critic are separate 3-hidden-layer MLPs (64 → 32 → 16, ReLU).

## Repository layout

```
.
├── src/                     # core package
│   ├── config.py            # all hyperparameters and I/O paths (Config class)
│   ├── data.py              # .xlsx instance loader (size-independent)
│   ├── env.py               # UPMSP-SDFS MDP environment + adaptive batching (Alg. 1)
│   ├── ppo.py               # actor/critic networks, policy, PPO update (Alg. 2)
│   ├── train.py             # training entry point (single-process or parallel)
│   ├── test.py              # scheduling/evaluation: rollout (Alg. 3) + scheduling (Alg. 4)
│   ├── metrics.py           # training/test metric tracking and plots
│   └── utils.py             # seeding, config snapshot
└── generate_datasets.py     # synthetic instance generator (paper Section 5.1)
```

The following directories are **created when you run the code**:

- `datasets/` — generated by `generate_datasets.py` (see below)
  - `D1/` 10 machines, 10 families, 500 jobs (1 train + 19 validation)
  - `D2/` 20 machines, 10 families, 1000 jobs (5 instances)
  - `D3/` 20 machines, 15 families, 1000 jobs (5 instances)
  - `D4/` 20 machines, 20 families, 1000 jobs (5 instances)
- `models/PPO_RAB/` — trained checkpoints written by `src.train`
- `results/PPO_RAB/` — training curves and evaluation results

### Dataset format

Each `Example_*.xlsx` instance has four sheets:

- **Jobs** — `Job Family | Demand | Weight | Due Date`
- **Machines** — `Machine | Initial Setup`
- **ProcessingTimes** — `Job Family / Machine | M1 … Mn` (`p_{i,f}`)
- **SetupTimes** — `From \ To | <families…>` (sequence-dependent, asymmetric `σ_{f,g}`)

A *job family* groups identical jobs that share weight, due date, and per-machine
processing time, with `Demand` copies each.

## Installation

Developed and tested with **Python 3.10**.

```bash
pip install -r requirements.txt
```

Main dependencies: `torch` 2.6.0, `numpy` 1.24.3, `pandas` 2.0.3,
`matplotlib` 3.7.2, `openpyxl` 3.1.5. The submission environment used the
CUDA 12.4 PyTorch build (`torch==2.6.0+cu124`); the code also runs on CPU.

## Usage

All paths and hyperparameters live in [`src/config.py`](src/config.py). Run the
scripts as modules from the project root.

### 1. Generate datasets

The `datasets/` folder is not shipped with the repository; generate it first,
reproducing the paper's data-generation procedure (Section 5.1):

```bash
python generate_datasets.py --out datasets            # all datasets -> datasets/
python generate_datasets.py --out datasets --only D2 D3
python generate_datasets.py --out datasets --seed 12345
```

### 2. Train

Trains on a single instance (`TRAIN_DATA_PATH`, default `datasets/D1/Example_1.xlsx`):

```bash
python -m src.train
```

Checkpoints are written to `models/PPO_RAB/` (`best_model.pt`,
`checkpoint_<N>.pt`, `final_model.pt`) and training curves to `results/PPO_RAB/`.

### 3. Evaluate / schedule

Loads `TEST_MODEL_PATH` and schedules every instance in each folder of
`TEST_DATA_PATH` (default `D2`, `D3`, `D4`) under a per-instance time limit:

```bash
python -m src.test
```

For each instance this writes a `schedule.csv`, a `convergence.csv`/`.png`
(best MWT over wall-clock time), and per-dataset / overall summary tables
(`test_results*.{json,csv}`) plus an MWT bar chart under `results/PPO_RAB/`.
